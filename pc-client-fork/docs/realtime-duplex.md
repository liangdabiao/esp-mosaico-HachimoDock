# 双向语音实现与验收

保留 USB 连接和现有蓝色气泡，实现宠物说话时仍可听见用户、确认用户插话后取消当前回复。不新增 LiveKit、Python sidecar、RTC 服务端、私有端点或凭据；USB 音频不是 WebRTC 协议。

0.1.80 更新：VAD 只触发候选识别，不再立即停播。流式 ASR 确认至少两个有效文字或单字「停」后才取消回复；空结果、普通单字、识别错误和超时均保留原回复。候选音频与等待时间有界，确认后复用同一识别流。下文早期实测的 VAD→flush 时间只描述旧的声学触发链路，不代表新版本包含云端确认的总打断延迟。完整策略及边界见 [实时对话](realtime-chat.md)。这轮通过离线回归及构建检查，尚未完成新版本 Windows/macOS 真人环境声对照验收。

## 参考与适配

参考 DeskBot V2 的 `audio_frontend_esp_sr.*`、`audio_player.cpp`、`rtc_gateway.py` 和 `rtc_barge_in.py` 的麦克风/播放参考拓扑、能力协商与打断边界。它使用 PDM 麦克风、Arduino 和 LiveKit；本项目使用 P4、ESP-IDF、ES7210/ES8311 和 Rust。因此按现有平台实现适配，没有复制其服务配置或引入其 Python/Arduino 运行时。

声音算法使用 [Espressif ESP-SR 2.5.3](https://components.espressif.com/components/espressif/esp-sr/versions/2.5.3) 的独立 AEC、NS、VAD API。完整 AFE 工厂会链接不需要的离线/神经网络模块，超过现有 OTA 分区容量，故不引入完整 AFE 工厂、唤醒词或离线指令模型。分区、形象和组件不变。

## PC 与固件

- 设备同时声明 `audioAec`、`audioVad`、`audioFullDuplex` 才开启双向收音；每帧还必须带 `aec: true` 和 `vadSpeech`。旧固件继续使用半双工。
- `listen_during_reply` 等待回复/播放时持续处理麦克风帧，保留 600 ms 预录；`listen_with_verified_barge_in` 在候选被流式 ASR 确认前保留原回复，确认后交接识别流，不丢弃排队的新语音。
- 取消当前 LLM 子任务，关闭当前 TTS 流，播放队列递增代次并丢弃旧 PCM/字幕。设备按播放 `sessionId` 忽略迟到旧帧。
- 未完整播报的任务确认作废；取消不会撤回已发出的家居指令，也不会自动重试。
- 设备 AEC 运行中失效时停止双向会话并显示错误，不将原始播放回声交给 ASR/工具。
- v1/v3 共用 16 kHz 单声道 PCM16、20 ms USB 帧；DSP 处理块单独适配。扬声器每次写入 20 ms，仅把送到 codec 的 PCM 加入参考，不用提前收到的整段 USB 音频。
- 当前候选使用 ESP-SR `AEC_MODE_VOIP_LOW_COST`（16 ms DSP 块）后执行降噪和 WebRTC VAD，不加额外数字增益；保留现有音量。物理链路仍是全双工，不受算法模式命名影响。音频任务固定在 core 0、优先级 18，高于视频解码/打包的 17/16，避免音频截止时间被动画任务挤占。
- ESP-SR 2.5.3 的实际 NS 库只接受 10 ms：每个 20 ms USB 帧分两次降噪，再执行 VAD，避免初始化断言。AEC 工作区和参考环形缓冲使用 PSRAM；先建立显示和 USB 接收任务，再初始化可选 DSP，避免抢占核心外设内存。
- 播放开始/取消/读取缓冲有互斥边界；写失败丢弃未播放参考，正常结束保留尾音参考。初始化失败、参考溢出、DSP 持续超时会撤销能力并回到保守模式。
- 每次播放 DMA 写入后主动让出一个调度节拍，避免高优先级播放线程立即重复占锁、饿死 USB 接收线程对播放会话的检查。ES8311 双向对话输入增益用 24 dB 留出 ADC 余量，退出/回退恢复 30 dB；扬声器仍为 100，ES7210 不套用这组增益。
- 音频回传绑定到开启采集的连接，不广播至无人读取的其他 USB 通道。音频发送使用驱动队列，不逐帧等待 TX 排空；采集时输出日志前检查队列已排空，若超时则跳过该条调试日志，防止直接写 FIFO 将日志插入 JSON 音频帧。固件/形象传输仍保留原 ACK 与排空路径。
- PC 按连接跟踪 `audio/begin/end/status`，音频和收音期间普通控制消息只分片写入，不暂停读取或同步排空；握手回复也遵循这一边界。一次卡顿的线程采样明确显示发送线程在 macOS `tcdrain`，接收线程在等待主动暂停标记；固件/形象传输保留原策略。修正后已完成多轮边播边收，无上述互等；长时间压力验收仍待完成。
- ASR 最终结果最多等待 8 秒，期间持续消费输入，用最多 576 帧的临时队列保留新语音。回复前先将它们送入 VAD，保留触发后的剩余帧，避免原 128 帧入口队列在约 2.56 秒后溢出。
- 处理后的人声需同时满足设备 VAD 与自适应能量门槛。安静聆听使用最低 RMS 96 / 5 帧（100 ms），回复期间仍使用 RMS 160 / 8 帧；每次启动候选最多容忍总计 2 帧有语音标记但能量不足的间隙，间隙不计入启动证据。设备 VAD 为 false 时立即清空启动计数。播放结束后 250 ms 保持严格门槛但不丢帧；已触发后的保持门槛最低 RMS 48，结束仍需 700 ms 静音。旧半双工 VAD 参数不变。600 ms 预录覆盖设备与 PC 的双重判定延迟；实际近端/远端人声灵敏度仍需实测。
- 新采集时间轴在 DSP 所属任务中重建 AEC/NS/VAD，避免跨会话复用旧时序的自适应状态；不在 USB 控制任务里销毁正在运算的句柄。
- USB/UART 的两个 32 KiB JSON 解析缓冲迁到 PSRAM（不是 DMA 缓冲，解析在任务中进行），释放 64 KiB 片内 RAM，不改变协议容量或 Flash 分区。
- 日志只记阶段、数量及耗时，不记录 PCM、原始对话或凭据。

## 实机验收清单

### 2026-09-21 漏识别修复与官方对照

0.1.71 使用反馈表明，安静播放验收不能替代真人近端识别验收。实际会话出现多次 ASR 启动但无文本，且没有原始录音，不能据此断言是哪一句丢失或是哪一层抑制。此次 PC 修复区分聆听与回复门槛、扩大句首缓存、容忍短能量间隙、检查 ASR 输入发送失败，并记录 `vad_window`、`asr_audio_submitted`、`asr_empty`。日志仅含帧数/能量/阶段，不保存语音内容。ASR 底层原本已保留非空中间结果，新增空终包回归，不把它误报为已确认根因。

官方资料核查（2026-09-21）：

- [P4 VAD 文档](https://docs.espressif.com/projects/esp-sr/en/latest/esp32p4/vadnet/README.html) 指出算法本身及最短人声判定会延迟首帧，AFE 用 `vad_cache` 补回句首。本项目以有界 PC 预录实现对应保障，不声称已接入 VADNet。
- [P4 AEC 文档](https://docs.espressif.com/projects/esp-sr/en/latest/esp32p4/acoustic_echo_cancellation/README.html) 推荐优先评估 FD_LOW_COST，且 NLP 等级仅对 FD 有效。当前 VOIP_LOW_COST 里的 VERYAGGR 不是已证实的人声抑制原因。FD 与 VOIP 的 DSP 块长不同，需比较回声误触发、近端识别与实时负载后再切换，不仅按模式名称选择。
- [官方 AFE 测试](https://github.com/espressif/esp-sr/blob/master/test_apps/esp-sr-afe/main/test_afe.cpp) 对比 SR/FD/VC、MR/MMNR、内部 RAM/PSRAM、feed/fetch 耗时及重复创建销毁泄漏。后续声学验收应同时比较这些指标，而不只看是否能初始化。
- [官方 WebRTC 示例音频层](https://github.com/espressif/esp-webrtc-solution/blob/main/solutions/openai_demo/main/media_sys.c) 使用 AEC 采集源，强调 ES8311 播放参考通道。本板当前采用软件参考，不能直接照抄示例的双声道硬件路由或 32 dB 增益。保留当前 USB/豆包链路，不为修复漏识别迁移云服务。
- 本地 ESP-SR 2.5.3 `esp_vad.h` 的 WebRTC VAD 模式越高越严格；不要照搬 VADNet 文档的模式灵敏度说明，两者不是同一实现。

本次是源码级修复，未自动替换运行中的应用或刷写设备，未改变固件 AEC 参数。新增合成帧回归不能代替轻声、短句、双讲的真实麦克风 → AEC → VAD → ASR 验收。

本轮实测（v1.3 / 0.7.59-p4，使用新 PC 判定）：约 32 秒设备播放期间采集 1,602 帧，VAD 误启动 0 次，音频故障 0 次，含播放前和结束后的聆听门槛检查。另用 Mac 扬声器播放合成固定句，经过真实设备麦克风/AEC/VAD/云端 ASR：电脑音量 16% 时 894 帧、设备人声标记 0、未触发（失败，不能用降低 PC 门槛解释全部漏听）；音量 50% 和 35% 两次均识别出目标关键句，分别返回 11 和 5 字。因此较弱输入的完整句首及真人双讲仍未验收，不能只凭关键句命中声称全文无丢失。电脑音量测试后恢复 16%，应用恢复原安装版本。

编译通过不等于声学效果验收。参考延迟需要按 codec/DMA/外壳校准；当前初始参考延迟为 4 ms。候选参数已有两轮各超过 32 秒的安静环境播放及一轮真人打断通过，但尚未完成连续多轮、近远距离、完整识别回复与长时间压力验收。未照搬 DeskBot 的 PDM 增益、播放期间禁止 VAD 的门控或“普通语音必须说满 1 秒”的限制。

1. v1/v3 分别最大音量播放 30 秒，无自打断、ASR 自回声及家居误执行。
2. 开场白、思考、TTS、播放时开口；分别测量 VAD→ASR 确认和确认→实际停声的延迟。后者目标 300 ms 内；前者受识别服务与网络影响，整体延迟以实测为准。
3. 近/远距离、风扇背景噪声、用户复述宠物原话，句首完整且能持续回复。
4. 连续打断至少 10 次，无旧音频/字幕复活、积压或断连。
5. 确认播报未结束时打断，不可批准旧任务；播放《唯一》、换歌等 5 步以内请求不触发确认，也不重复控制。
6. 旧版回退、断线、AEC 故障、退出恢复 Agent 跟随、按键语音正常。

0.1.71 内部验证包配套 0.7.59-p4 的 v1/v3 镜像；开发镜像保留真实的 `-dirty` 身份，仅用于内部验证，不作为全场景已验收的公开版本发布。

## 0.1.72：句首缓存与 FD 模式实机对照

在同一块 v1.3、同一套麦克风/扬声器上做了保留数据的 A/B OTA。默认固件为 VOIP_LOW_COST；候选为隔离构建 `esp32_p4_aec_fd_bench`（FD_LOW_COST + AGGR，版本 `0.7.59-p4-fdbench`）。测试不执行家居操作，不保存设备录音。

| 项目 | VOIP_LOW_COST | FD_LOW_COST + AGGR |
| --- | --- | --- |
| 同一 WAV、约 32 秒设备播放 | 0 次 VAD 误触发 | 4 次 VAD 误触发 |
| 电脑发声 50%，近端固定句 | 300/600 ms 均全文一致 | 两种缓存均为空文本 |
| 电脑发声 35%，近端固定句 | 300/600 ms 均全文一致 | 未形成完整语句，未进入最终识别 |

缓存对比从同一次真实收音取数据，仅将触发前的缓存裁为 300/600 ms，后续音频相同，依次送云端 ASR；云端执行时刻不同，结果仍存在服务随机性。两种 AEC 的近端刺激使用相同文本/音色，但分别合成，不能冒称是逐采样相同的输入；播放回声实验使用的是同一 WAV。电脑发声百分比不是校准声压，也不代表真人距离。

FD 的 42 个性能统计窗口平均每 20 ms 输入耗时约 3.63 ms、观测单次最大 8.79 ms，但速度优势不能弥补误触发和近端识别失败。结论仅适用于此次板级参数，不能推广为所有 FD 模式都不合适。此候选未进入安装包。

上述为首轮比较。恢复 VOIP 后复核时，原聆听门槛 RMS 80 / 3 帧在播放结束约三秒后出现一次低能量触发（触发帧 RMS 114.4），播放期间仍为零；这属于未通过的边界用例，不应隐藏。最终候选将聆听门槛调为 RMS 96 / 5 帧，增加对应低能量/短突发回归，并重新构建安装包。不能把某一轮零误触发概括为所有环境稳定。

最终 RMS 96 / 5 帧候选：32 秒播放期间仍为零误启动，但播放结束后又出现一次低能量触发（RMS 114.2）；播放前也观察到 5 帧人声标记，现场安静条件尚未确认，无法仅凭这些指标判定来源。该轮声学零误触发验收为失败，不据此继续盲目抬高阈值。最终候选随后在电脑音量 35% 的近端测试中，300/600 ms 两条路径均识别出完整固定句（11 字）。该候选尚未完成安静条件复核和真人双讲验收，此历史测试不作为当前公开版本的验收结论。最终电脑音量恢复 16%。

0.1.72 保留 VOIP 固件 0.7.59-p4（v1/v3 均内置），采用 PC 分场景 VAD 与 600 ms 缓存。缓存扩大是对触发延迟的余量保护，本轮没有测出相对 300 ms 的识别率收益。实机已从 FD 候选恢复包内 v1 固件，OTA 检查通过且镜像状态为 valid。v3 本轮没有实机，不能以二进制校验代替声学验收。

## 可复现实验入口

`live_device_near_end_asr`（仅 macOS，默认跳过）：要求独占串口与已验证板 ID，使用临时合成测试 WAV 从电脑扬声器发声，设备麦克风采集并经过生产 VAD 送到 ASR，只核对固定关键句，不执行 LLM/工具。测试结束清理 WAV，不保存设备录音或原始识别文本；必须记录发声设备、音量和测试局限，不能冒充真人双讲。

云端链路回归：`live_voice_pipeline` 连续三轮通过 TTS 合成测试输入 → 真实 ASR → 真实大模型 → 真实 TTS；每轮在 TTS 首段 PCM 后注入测试人声帧，经生产 VAD 取消合成，再确认下一次 TTS 能正常完成。该测试验证取消/恢复和服务连接，不以合成输入冒充真人多轮对话。实际豆包 TTS 另通过设备全双工收音测试，首轮 184 帧、零回声触发，随后四秒收音 128,000 字节。

`live_device_duplex_echo_probe` 为默认跳过的硬件测试，必须显式提供串口、预期板 ID 和 16 kHz 单声道 PCM16 测试 WAV；不调用云端 ASR 或家居工具。`P4_ECHO_REPEAT=2` 延长播放，音频总长限制为 40 秒。

`P4_ECHO_BARGE=1` 为需用户配合的测试：开始后约 7 秒显示蓝色气泡提示说话；此前不允许出现 VAD 启动，提示后检测到语音就经过实际播放器队列发送 flush，等待设备 `playback_flushed`。报告的是 **VAD 到设备 flush 确认**，不冒充“人开始说话到听到停声”的总延迟；codec DMA 另有至多约 30 ms 尾音。未经用户在场配合不能把这一测试记为已通过。
